The finite budgets are **at most 15,000 PPO updates per stage** (Stage 2 is additional), and 24 GPU-task wall hours per stage, whichever is reached first, including startup and evaluation. These are caps, not a requirement to train to the cap. The original README's 15,000-update examples concern the original 8192-env Object/Climb tasks; they do not certify convergence of this 4096-env continuous-carry task. Benchmarks have 1800-second task timeouts, finite candidates, and no retries after instability. Configurable limits are recorded in each run's `config.json`; pass `start --config /absolute/path/custom.json` for a new run. Training iteration caps, evaluation cadence and stagnation settings reload at window boundaries. Stage budgets, iteration caps, disk floor and per-task timeouts are all enforced. A restart conservatively charges interrupted task elapsed time, including downtime, to avoid undercounting. Exact hardware metered active GPU time is not claimed.

The state machine is `BENCHMARK -> STAGE1 -> EVAL1 -> STAGE2 -> EVAL2 -> COMPLETED/BLOCKED`, with repeated training/evaluation windows inside each stage. A process lock and a shared GPU lock prevent duplicate carry launches. Every GPU task checks NVIDIA compute-process ownership before launching. Training and evaluation never overlap. GPU memory/utilization are sampled every second; active process/log/metrics are reviewed every 60 seconds; quantitative JSON reports are written every five minutes. Persistent physics errors, NaNs, OOM/headroom exhaustion, disk floor or budget exhaustion stop the run.

The user subsequently requested **direct 4096 validation, then fixed 4096 training**. The active config and new-run defaults now use `candidates=[4096]`, `fixed_num_envs=4096`; 8192 is excluded. Earlier completed 256/512/1024/2048 measurements are preserved. Each candidate runs one fresh physics/PPO smoke update, then two warmup updates and eight measured updates in a fresh throughput process. A separate one-update resume test verifies exact model, optimizer, normalization and stored curriculum loading from the previous candidate. All candidates use 24 rollout steps, **1536 samples/minibatch and five epochs**, with minibatches `num_envs/64`. Samples per iteration still scale with environment count; throughput is not proof of equivalent convergence. 4096 must pass stability and at least 4 GiB memory headroom before selection; failure blocks training rather than forces it. No contact buffer/solver changes are made. Evidence and decisions go to `benchmark_results.csv`, `benchmark.png`, `benchmark_report.md`, and per-job JSON/logs. To explicitly restore automatic throughput selection in a future config, set `fixed_num_envs=null` and the desired finite candidate list.

Stage 1 starts from scratch with `exp:g1-29dof-wbt-hybrid-carry`, `track_ratio=1.0`. Per the user's updated instruction, both stages evaluate first after 2000 PPO updates and then every 2000 updates (Stage 2 counts from its own initialization). Recoverable full checkpoints and adjacent Actor exports are saved every 50 updates and at every process exit. Each evaluation runs all three reference clips from frame zero, with 10 seeded joint-reset perturbations per clip (0.002 rad standard deviation); the two moving clips are approximately 2.2 s and static clip approximately 4 s. Clip timeouts count as completion only when no physical/tracking failure coincides. No 20 s reference is invented.

Stage 1 per-seed success requires full-reference completion, at least 80% of steps with bilateral forces above 0.5 N, upward support at least half box weight and contact quality at least 0.4, maximum box tilt <=0.45 rad, minimum box height >=0.4 m, maximum robot-box separation <=0.9 m, mean robot/object positional error <=0.15 m, mean robot orientation error <=0.35 rad and object orientation error <=0.45 rad. Every clip needs at least 80% successful seeds. A promising checkpoint must repeat the gate on **30 seeds** before Stage 2. Precise thresholds are stored in `gates.json` and each evaluation JSON.

Selection uses physical success and survival/support/tracking evidence: `0.6*success + 0.2*duration_fraction + 0.1*support_fraction + 0.1*exp(-object_error/.15-robot_error/.15)`, averaged over seed/scenario trials. This allows partial progress to be measured before any clip succeeds. Training reward and loss curves are supporting diagnostics; they cannot independently establish convergence. Three consecutive evaluation windows without more than 0.01 improvement trigger a quantitative diagnosis of contact forces, weight support, box/robot balance, tracking, rewards and failure distribution. Before stopping for stagnation or the iteration cap, the best physically ranked checkpoint receives a final **30-seed** assessment when resources remain. Results go to `stage1_final_assessment.json/.md` or `stage2_final_assessment.json/.md`; failed physical qualification ends as **BLOCKED**, preserving the best intermediate policy. A successful 30-seed gate permits advancement or completion even before the cap. No automatic corrective changes to physics, rewards, references or gates are made. Retargeted moving references remain unproven dynamically; prior reset evidence certified only 0.2 s and some PD holds dropped about 0.10 m by 0.5 s.

Stage 2 starts only from the exact checkpoint that passed the final Stage 1 gate. Actor/Critic parameters, empirical normalizers, optimizer moments, carry curriculum counters/history and adaptive sampler state are restored. Environments are initially 50/50 Track/Gen, with the same 348D Actor and four external commands `[vx,vy,yaw_rate,pelvis_height]`. There are no terminal goals, reference phase or clip IDs in the Actor. Physical object observations remain. Existing levels 0..4 are learned in order; advancement needs >=100 completed Gen episodes with >=70% physical timeout success, at least 5 s duration and >70% good tracking/support steps. An episode ending in failure cannot count as curriculum success. No level is forced.

Reference-free evaluation uses only exported ONNX+Actor metadata, physical assets and static reset. Both reference loader constructors are replaced by hard failures before environment creation. It tests hold, forward/backward, lateral +/-, yaw +/-, low/high height, combined commands, forward-stop-forward and multiple command changes without resetting. Required curriculum levels are reported; tests beyond the trained level are labeled unsupported probes. Every command has at least 10 seeds, increasing to 30 for final acceptance. Goal episodes target 20 continuous seconds. Metrics are captured before automatic reset, and a seed stops accumulating after its first reset/failure. Surviving time after restart is never included.

Goal acceptance requires >=80% successful seeds for **all** scenarios at curriculum level 4, using the same physical gates, and command errors <=0.10 m/s per velocity axis, <=0.15 rad/s yaw, <=0.03 m height for >=90% of steady-command time (one-second settling excluded after a change). Unsupported capabilities cannot pass final acceptance. Reports contain per-seed survival/errors/support/tilt/drop/separation and multi-cause failure counts; success plots and raw pre-reset physics are retained. Short simulation videos are optional and not enabled by default.

Checkpoint writes use a temporary file, full CPU deserialization/finite-state/schema/optimizer validation, fsync, atomic replacement, and checksum commit records. Discovery scans real indexed `model_XXXXX.pt` files. A missing/mismatched commit record, partial serialization or nonfinite state is rejected; discovery falls back to older valid checkpoints. ONNX publication is atomic per file and has checksums; selection checks the adjacent ONNX graph and Actor metadata. Resumed runs start after the last completed iteration. Live simulator state is reset on resume; bitwise continuation of trajectories/RNG is not claimed. Previous checkpoints and experiments are preserved. No large artifact is pushed to GitHub.

Artifacts distinguish verified pipeline engineering, physically learned carrying, learned independent four-command tracking, and unmet capabilities. At deployment time, only measured physical evaluations establish policy capability. A running PPO loop is never reported as success.
